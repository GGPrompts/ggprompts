## Findings

### Design Philosophy

SQLite was born from a practical frustration: Richard Hipp was building battleship software for the US Navy and kept having the Informix database server crash. He asked, "Why do we even need a server? Why can't I pull this directly off the disk drive?" The result is a **serverless, zero-configuration, self-contained** database engine that runs in-process with the application.

Core principles:
- **"Your enemy is complexity"** — solve the actual problem, not a theoretical one
- **Self-reliance** — Hipp built his own parser generator (Lemon), his own VCS (Fossil), his own printf(), his own malloc wrappers — no external dependencies beyond the C compiler
- **Replacement for fopen()** — SQLite positions itself not as a replacement for PostgreSQL/MySQL, but as a replacement for custom file formats. Reading data from SQLite is faster than reading individual files from the filesystem
- **Backwards compatibility** — the file format has been stable since 2004 (version 3.0.0) and is guaranteed to remain compatible through at least 2050
- **Single-file database** — the entire database (schema, tables, indexes, metadata) lives in one cross-platform binary file. No directory structures, no server processes, no configuration files
- **Public domain** — not even open source; fully public domain with no license restrictions

Hipp developed SQLite independently of academic database theory, discovering convergences with PostgreSQL's architecture organically. He learned B-trees directly from Knuth's *Art of Computer Programming*.

### The Amalgamation Build

SQLite is distributed as a single C source file called **sqlite3.c** — the "amalgamation." It is generated by concatenating **111+ separate C source files** plus 22 extension files into one file (~238K lines, ~8.4 MB). This exists for two reasons:

1. **Deployment simplicity** — one file to track and compile
2. **Performance** — compilers perform better inter-procedure and inlining optimizations on a single translation unit, yielding **5-10% faster code**

The amalgamation is built using TCL scripts (`./configure && make sqlite3.c`). A "split amalgamation" variant exists for debuggers that choke on files over 32K lines.

### Component Architecture & Data Flow

SQL processing flows through a clean pipeline of seven layers:

```
SQL Text → Tokenizer → Parser → Code Generator → VDBE (Bytecode VM) → B-Tree → Pager → OS Interface (VFS) → Disk
```

Each layer only communicates with its immediate neighbors. The top three layers implement `sqlite3_prepare_v2()` (compilation), while the bottom four implement `sqlite3_step()` (execution).

#### 1. Tokenizer (`tokenize.c`)
- Hand-coded lexer (not generated) that breaks SQL text into tokens
- **Key design choice**: the tokenizer calls the parser (not vice versa), making it naturally thread-safe and faster
- Feeds tokens sequentially to the parser one at a time

#### 2. Parser (`parse.y` → generated by Lemon)
- Uses **Lemon**, Hipp's custom LALR(1) parser generator (not YACC/Bison)
- Lemon advantages over YACC: reentrant, thread-safe, includes non-terminal destructors to prevent memory leaks, generates a single C file
- Builds a parse tree from the token stream

#### 3. Code Generator
- The largest and most complex component, spread across many files:
  - `select.c`, `insert.c`, `update.c`, `delete.c` — statement-specific code generation
  - `where.c`, `wherecode.c`, `whereexpr.c` — WHERE clause optimization and the **query planner**, which evaluates millions of possible algorithm combinations to find the optimal plan
  - `expr.c` — expression code generation
  - `build.c` — CREATE/DROP statements
  - `trigger.c`, `attach.c`, `vacuum.c`, `pragma.c` — specialized handlers
  - `auth.c` — authorization callbacks via `sqlite3_set_authorizer()`
- Output: a `sqlite3_stmt` object containing VDBE bytecode

#### 4. Virtual Database Engine — VDBE (`vdbe.c`)
- A **register-based bytecode virtual machine** (changed from stack-based in SQLite 3.0)
- Each instruction has an opcode plus up to five operands (P1-P5)
- Key files: `vdbe.c` (the entire VM in one file), `vdbeaux.c` (utilities), `vdbemem.c` (value storage for strings/ints/floats/BLOBs), `vdbeapi.c` (external interface)
- Implements SQL functions via C callbacks; built-in functions in `func.c` (abs, count, substr, etc.) and `date.c`
- Can be traced with `PRAGMA vdbe_trace=ON` to see bytecode execution step by step
- Key opcodes: `OpenRead`/`OpenWrite` (cursor management), `Column` (extract data), `Rewind`/`Next` (iteration loops), `MakeRecord`/`PutIntKey` (record construction and storage), `Transaction`/`Commit` (transaction control)
- Uses a **two-pass pattern** for UPDATE/DELETE: first pass identifies target rows (storing keys in a temporary list), second pass modifies them — necessary because modifying a B-tree during traversal would invalidate cursor positions

#### 5. B-Tree Layer (`btree.c`, `btree.h`)
- Maintains all data on disk using B-tree structures
- **Two B-tree variants**:
  - **Table B-trees** (leaf data): store row data in leaves, keyed by 64-bit signed integer rowid
  - **Index B-trees** (leaf index): store arbitrary keys with no associated data
- One B-tree per table, one per index, all stored in the same single database file
- Requests fixed-size pages from the page cache below
- The schema itself is stored in `sqlite_schema` (page 1), a table B-tree containing CREATE statements for all tables, indexes, views, and triggers

#### 6. Page Cache / Pager (`pager.c`, `wal.c`, `pcache.c`, `pcache1.c`)
- Views the database as an array of uniform-sized pages (default 4096 bytes, configurable 512–65536, must be power of 2)
- Handles reading, writing, and caching pages in memory
- Manages **atomic commit and rollback** — this is where ACID guarantees are enforced
- Manages file locking for concurrency control
- Maximum database size: ~281 TB (2^32 - 2 pages x 65536 bytes/page)

#### 7. OS Interface — VFS (`os_unix.c`, `os_win.c`)
- **Virtual File System** abstraction with three objects:
  - `sqlite3_vfs` — VFS definition (open, delete, check existence, get randomness, get time)
  - `sqlite3_file` — open file handle
  - `sqlite3_io_methods` — file operations (xRead, xWrite, xSync, xLock, xUnlock, xClose, xTruncate, xFileSize)
- Built-in implementations:
  - **Unix**: 5 variants — `unix` (POSIX advisory locks, default), `unix-excl` (exclusive), `unix-dotfile`, `unix-none` (no locking), `unix-namedsem` (VxWorks)
  - **Windows**: 4 variants — `win32` (default), `win32-longpath`, `win32-none`, `win32-longpath-none`
- **VFS Shim pattern**: thin wrappers that intercept calls and delegate to an underlying VFS. Examples: `vfstrace` (logging), `quota` (file size limits, used by Firefox), `test_multiplex` (split large DBs across files), `appendvfs` (append DB to an executable)
- Custom VFS enables SQLite on embedded devices without filesystems, in-memory databases, encrypted databases, etc.
- Porting SQLite to a new OS = writing a new VFS implementation

### Single-File Database Format

The entire database is one binary file with a 100-byte header starting with the magic string `"SQLite format 3\000"`.

**Header fields** (selected):
| Offset | Size | Field |
|--------|------|-------|
| 0 | 16 | Magic string |
| 16 | 2 | Page size (bytes) |
| 18-19 | 2 | File format version (1=rollback journal, 2=WAL) |
| 24 | 4 | File change counter |
| 28 | 4 | Database size in pages |
| 40 | 4 | Schema cookie (incremented on schema change) |
| 56 | 4 | Text encoding (1=UTF-8, 2=UTF-16LE, 3=UTF-16BE) |
| 96 | 4 | SQLite version number that created the DB |

**Page types**:
- `0x0d` = Table B-tree leaf (rowid + data)
- `0x05` = Table B-tree interior (rowid + child pointers)
- `0x0a` = Index B-tree leaf (keys only)
- `0x02` = Index B-tree interior (keys + child pointers)
- Freelist trunk/leaf pages (unused page tracking)
- Overflow pages (for cells too large for one page)
- Pointer map pages (for auto_vacuum)

**Record format** uses variable-length integers (varints, 1-9 bytes) and serial type codes:
- 0 = NULL, 1-6 = integers (1-8 bytes), 7 = IEEE 754 float, 8-9 = constants 0/1
- N >= 12 even = BLOB of (N-12)/2 bytes
- N >= 13 odd = text of (N-13)/2 bytes

### Locking and Concurrency Model

SQLite uses a **five-state file locking protocol** for multi-process concurrency:

```
UNLOCKED → SHARED → RESERVED → PENDING → EXCLUSIVE
```

| State | Who holds it | What it means |
|-------|-------------|---------------|
| **UNLOCKED** | Nobody | Default; no reads or writes |
| **SHARED** | Multiple readers | Can read; prevents writers from committing |
| **RESERVED** | One writer (planning) | Intends to write; other SHARED locks still allowed; other RESERVED locks blocked |
| **PENDING** | One writer (waiting) | About to write; no NEW shared locks allowed; existing readers can finish |
| **EXCLUSIVE** | One writer (writing) | Actually writing to disk; no other locks of any kind |

**Key design**: PENDING prevents writer starvation — without it, a continuous stream of readers could starve a waiting writer indefinitely.

Implementation:
- **Unix**: POSIX advisory file locks (`fcntl`)
- **Windows**: `LockFile()` / `LockFileEx()` / `UnlockFile()`
- Lock conflicts return `SQLITE_BUSY` immediately (no blocking waits)

### Journal Modes: Rollback Journal vs WAL

#### Rollback Journal (default)
- Before modifying a page, the **original content** is copied to a journal file (`<database>-journal`)
- Changes are written directly to the database file
- **Commit** = deleting/truncating the journal file (this is the atomic commit point)
- **Crash recovery**: if a "hot journal" exists on open, SQLite replays it to restore the original state
- Writes data **twice** (once to journal, once to database)

#### Write-Ahead Log (WAL mode)
- Enabled with `PRAGMA journal_mode=WAL`
- Original database pages are **preserved**; changes are **appended** to a WAL file (`<database>-wal`)
- **Commit** = appending a commit record to the WAL (no database file writes needed)
- **Readers** check WAL first, then fall back to the database file
- Each reader records an "end mark" — the last valid commit at transaction start — providing snapshot isolation

**WAL advantages**:
- **Concurrent readers and writer** — readers never block writers, writers never block readers
- Writes happen only once (to WAL), not twice
- Sequential I/O only (appending to WAL)
- Fewer `fsync()` calls needed

**WAL components**:
- **WAL file** (`<database>-wal`): sequential log of modified pages in "frames"
- **WAL-index** (`<database>-shm`): memory-mapped shared-memory file for fast page lookups; rarely exceeds 32 KB; never synced to disk

**Checkpointing**: periodically transfers WAL content back to the database file
- **Automatic**: triggered at 1000 pages (~4 MB) by default
- **Types**: PASSIVE (non-blocking), FULL (tries harder), RESTART (forces completion)
- A long-running reader can block checkpoint completion (its end mark prevents overwriting pages it might still need)

**WAL limitations**:
- All processes must be on the same host (shared memory requirement)
- Does not work over network filesystems
- Mostly-read workloads are ~1-2% slower than rollback journal
- Large transactions (>100 MB) can be slower

### Extension Architecture

SQLite supports **run-time loadable extensions** via shared libraries:

**Loading mechanism**:
```c
sqlite3_load_extension(db, "filename.so", "entry_point", &errmsg);
// or in SQL:
SELECT load_extension('filename.so');
```

**Entry point convention**: `sqlite3_X_init` where X is derived from the filename. Extensions receive a pointer to the `sqlite3_api_routines` structure containing all SQLite API functions.

**Extension loading disabled by default** for security; must be explicitly enabled via `sqlite3_db_config()`.

**Platform implementation**: Unix uses `dlopen()`/`dlsym()`, Windows uses `LoadLibrary()`/`GetProcAddress()` — abstracted through the VFS layer's `xDlOpen`/`xDlSym`/`xDlClose` methods.

**`sqlite3_auto_extension()`** — registers an extension to be automatically loaded for every new database connection. Extensions can return `SQLITE_OK_LOAD_PERMANENTLY` to stay in memory after the connection closes.

#### Notable Built-in Extensions

All compiled into the amalgamation but disabled by default (enabled with `-DSQLITE_ENABLE_*` flags):

**FTS5 (Full-Text Search 5)**:
- Virtual table module for efficient text search across document collections
- Implements a **segmented inverted index** architecture: each transaction creates a small B-tree segment; segments are periodically merged into larger ones (balancing write speed vs query cost)
- Index stores: document rowid, column number, and token offset for each term
- Pluggable tokenizers: `unicode61` (default, Unicode-aware), `ascii`, `porter` (stemming), `trigram` (substring matching)
- Built-in BM25 ranking function (Okapi BM25 algorithm) with per-column weighting
- Supports phrase matching, proximity queries (NEAR), prefix queries, boolean operators, column filtering
- Three content modes: standard (stores content), contentless (index only), external content (synced via triggers)
- Backing tables: `%_idx`/`%_data` (segments), `%_docsize` (token counts), `%_content` (optional), `%_config`

**R-Tree (Spatial Index)**:
- Virtual table implementing R*-Tree spatial indexing (Beckmann et al., 1990)
- Efficient for range queries on multidimensional data (1-5 dimensions)
- Use cases: geospatial queries, CAD systems, time-interval queries
- Stores coordinates as 32-bit floats (`rtree`) or 32-bit integers (`rtree_i32`)
- Three shadow tables: `%_node` (tree structure), `%_parent` (parent-child links), `%_rowid` (entry-to-node mapping)
- Supports auxiliary columns (since 3.24.0) and custom query geometry callbacks via MATCH
- Coordinates rounded outward to prevent false negatives from float precision

**JSON1**:
- SQL functions for creating, parsing, and querying JSON data
- `json()`, `json_extract()`, `json_insert()`, `json_set()`, `json_remove()`, `json_type()`, `json_array()`, `json_object()`
- `json_each()` and `json_tree()` table-valued functions for iterating JSON structures
- Internal JSONB binary format for efficient storage and manipulation

**Other extensions**: RBU (Resumable Bulk Update), SESSION (changeset tracking), DBSTAT (page-level statistics virtual table)

### Testing Methodology

SQLite has one of the most rigorous testing regimes of any software project:

**Scale**: 155.8K lines of source code vs ~92 million lines of test code — a **590:1 test-to-code ratio**.

**Four independent test harnesses**:

| Harness | Type | Test Cases | Purpose |
|---------|------|-----------|---------|
| **TCL Tests** | Public domain | 51,445 distinct cases | Primary development tests; 1,390 files, 23.2 MB |
| **TH3** | Proprietary C | 50,362 cases (~2.4M parameterized) | 100% MC/DC branch coverage; embedded platform testing |
| **SQL Logic Test** | Cross-DB | 7.2 million queries | Compares results against PostgreSQL, MySQL, SQL Server, Oracle |
| **dbsqlfuzz** | Proprietary fuzzer | ~500 million cases/day | Mutates SQL AND database files simultaneously; 16 cores continuous |

**100% MC/DC (Modified Condition/Decision Coverage)**:
- Adopted from aviation industry standard DO-178B
- Every branch in the code tested in both directions
- "Once we got to that point, we stopped getting bug reports from Android" — Richard Hipp
- 6,754 assert statements throughout the codebase
- 1,184 `testcase()` macros verify boundary conditions

**Anomaly testing**:
- **OOM testing**: simulates malloc() failure after N allocations; loops until operation succeeds without error
- **I/O error testing**: custom VFS injects disk failures; validates `PRAGMA integrity_check` after each
- **Crash testing**: simulates power loss mid-transaction; validates atomic rollback
- **Compound failures**: stacks multiple failure types (e.g., I/O error during crash recovery)

**Fuzz testing evolution**:
- AFL (2015-2019), Google OSS Fuzz (continuous), and the current primary: **dbsqlfuzz**
- dbsqlfuzz is structure-aware: mutates both SQL input and the database file together
- Since adoption, external fuzzer bug reports have "all but stopped"
- **jfuzz** (2024): specialized fuzzer for JSONB corruption

**Dynamic analysis**: Valgrind, `-fsanitize=undefined` (Clang), `-ftrapv` (GCC), `/RTC1` (MSVC), custom `SQLITE_MEMDEBUG` memory wrapper

**Mutation testing**: compiles to assembly, systematically flips branch instructions, verifies test suite catches each mutation

**Static analysis**: zero warnings under GCC `-Wall -Wextra`, MSVC, and Clang scan-build

**Release process**: ~200-item manual checklist, minimum 3 days of testing across multiple platforms (big/little endian, 32/64-bit, ARM/Intel, Windows/Linux/BSD), "veryquick" subset of ~304.7K cases run before every source tree check-in
